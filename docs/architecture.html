Tiny Happy People architecture

The database, the scheduled jobs, the outside services and the survey flow. For the weekly message pipeline, incoming SMS and a parent's journey, see architecture.md.

System context

The app runs on Heroku as a web dyno (Puma) and a worker dyno (Solid Queue), both using one Postgres database. Solid Queue keeps its jobs in that same database. All SMS goes out from background jobs. Delivery receipts and replies come back to the web dyno as webhooks (dashed lines): AWS sends them through SNS to /messages/aws_*, Twilio posts to /messages/twilio_*. Both dynos report errors to AppSignal, and AWS SES emails the team their login links and alerts about new replies.

  • Every users row has an sms_provider (aws by default, or twilio). Sms::Client uses it to pick an adapter. Nothing is sent unless SMS_ENABLED is "true".
  • Webhooks are checked before they're used: the SNS message signature for AWS, and X-Twilio-Signature for Twilio.
  • The /admin area, Blazer, Skadi and Mission Control (/jobs) are only for signed-in admins (Devise).

Scheduled jobs

Everything in config/recurring.yml, laid out as a week. The four weekly-message runs happen every day, but each one only messages parents whose day_preference is today. Most other jobs pick their parents with a User scope, then enqueue one job per parent through SendBulkMessageJob.

  • Every hour, on the hour: RetryFailedMessagesJob resends messages that failed in the last hour.
  • Time zone: Solid Queue reads these times in the server's time zone. On Heroku that's UTC unless the TZ config var is set, so in summer 07:00 would be 08:00 UK time. config.time_zone isn't set either, so Time.zone.today (used to choose the day's parents) is also UTC.
  • 11:00 is the busiest slot: the afternoon message, restarts from the waitlist, Tuesday nudges and Friday offboarding warnings all start then. They share the worker's 3 threads and the 15-a-second SMS batching.
  • Jobs that aren't scheduled: these run when something happens. Welcome and waitlist messages run on sign-up. Surveys run after a set number of messages. The offboarding survey runs a week after the last message. Broadcasts run when an admin sends one. Auto-replies, admin emails and status updates run when a webhook arrives.

Survey flow

Surveys are mainly for the Wales cohort. A survey_sends row records that a parent was sent a survey. Its completed_at is set when they submit. Survey links use the parent's survey_token, a short code stored on users, so they don't expire.

Messaging

Parents sign up as users and are put in a group. Each group has a sequence of contents keyed by the child's age in months. Every SMS is a message, either from the content programme or from an admin's broadcast.
